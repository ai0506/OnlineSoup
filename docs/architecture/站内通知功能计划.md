# 站内通知功能计划

> 状态：待实施  
> 范围：OnlineSoup（汤局）的注册用户站内通知  
> 本文是实施计划，不代表功能已上线；以实施后的迁移、权限和代码验证为准。

## 1. 目标与边界

提供管理员操作、注册用户在主页查看的持久化站内通知工具。

- 管理员可向全部注册用户或指定注册用户发送通知。
- 用户登录后可在主页查看自己的通知、区分未读与已读，并手动标记已读。
- 通知可附一个站内跳转路径，例如 `/feedback`；正文不执行 HTML。
- 管理端可查看已发送通知及送达人数、已读人数。

第一版不包含真实邮箱、Resend 邮件、浏览器权限、Web Push、手机推送、访客离开房间后的持久化通知、玩家私信，或用房间聊天消息替代全站通知。

“全部用户”指发送时已经存在的注册账户；未来注册的账户不自动补收历史通知。

## 2. 现有实现与取舍

现有 `flash` Cookie 只保存一条、有效期 60 秒，适合页面跳转结果，不能记录未读或通知历史。`room_messages` 要求房间和座位归属，仅适合当前房间事件；不能承载全站或指定账户通知。

因此通知使用独立数据，不复用上述机制，也不影响房间、座位、积分、AI 请求或题目状态。

可复用的现有能力：

- `src/app/page.tsx` 已在主页识别登录账户，适合读取“我的通知”。
- `src/components/site-header.tsx` 已读取登录用户资料，后续可选加未读角标，但不是第一版前置条件。
- `/admin` 已有二次验证、按 tab 懒加载、操作反馈和账户用户名搜索。
- `user_feedback` 使用私有表与受保护 RPC 的模式，适合作为权限边界参考。

## 3. 数据模型

采用“通知内容”和“收件人状态”分离的结构，避免群发时复制正文：

```text
notifications
  id              uuid primary key
  title           text not null                 -- 1 到 120 字
  content         text not null                 -- 1 到 2000 字，纯文本
  link_path       text null                     -- 仅允许站内相对路径
  created_by      uuid null -> profiles.id      -- 管理员删除后置空
  created_at      timestamptz not null

notification_recipients
  notification_id uuid -> notifications.id      -- 删除通知时级联删除
  user_id         uuid -> profiles.id           -- 删除账户时级联删除
  read_at         timestamptz null
  primary key (notification_id, user_id)
```

索引：

- `notification_recipients(user_id, read_at, notification_id)`：主页的未读数和最新通知查询。
- `notifications(created_at desc)`：管理端历史列表。

不存储邮箱、设备、IP、访客 Cookie 或浏览器订阅信息。`created_by` 只供后台审计，绝不返回给普通用户。

## 4. 权限与 RPC

新表均启用 RLS，并撤销 `anon`、`authenticated` 与 `public` 的直接表权限。浏览器不直接读写表。

新增 RPC：

1. `admin_create_notification(...)`
   - 仅授予 `service_role`；由已通过 `requireAdmin()` 与二次验证的 Server Action 调用。
   - 在同一事务写入通知和“全部”或指定 `profile.id` 的收件人记录。
   - 目标去重、校验目标账户存在，不允许空目标。

2. `get_my_notifications(p_limit integer default 20)`
   - 仅用 `auth.uid()` 查询当前账户。
   - 只返回标题、正文、合法站内路径、创建时间和 `read_at`。

3. `mark_my_notification_read(p_notification_id uuid)`
   - 只更新 `user_id = auth.uid()` 的未读记录，幂等写入 `read_at`。
   - 不接受用户 ID，防止越权标记他人通知。

所有 `SECURITY DEFINER` 函数须设置空 `search_path`，撤销 `PUBLIC` 执行权限后再授予所需角色，并执行 `notify pgrst, 'reload schema'`。

## 5. 界面与交互

### 用户主页

仅登录用户显示“通知”区域：

- 显示未读数和最新 20 条通知；未登录用户不显示。
- 每条显示标题、发布时间、正文、可选站内跳转按钮和“标记已读”。
- 未读有清晰但不过度打扰的样式；正文使用普通 React 文本渲染，不使用 `dangerouslySetInnerHTML`。
- 第一版不做实时弹窗；刷新主页或重新登录可得到最新结果。

### 管理后台

在 `/admin` 新增“通知”主 tab，沿用现有按 tab 取数和站内确认弹层：

- 收件人模式：全部注册用户 / 指定用户。
- 指定模式按用户名搜索、多选现有账户，提交 `profile.id`。
- 填写标题、正文和可选站内路径；发送前展示预计收件人数并二次确认。
- 历史列表显示创建时间、标题、总收件人数和已读人数；第一版不展示其他用户的个人状态明细。

原“邮件发送”tab 保持原样，不接入本功能。

## 6. 实施顺序

1. 新建 Supabase 迁移：表、索引、RLS、授权、三个 RPC 和 schema reload。
2. 新增共享 TypeScript 类型、通知查询/标记入口与 Zod 校验。

5. 视使用反馈增加头部未读角标；该步骤不阻塞第一版。

## 7. 验收与安全检查

数据库检查：

- 公开 key 的匿名用户不能读取或更新通知。
- 账户 A 只能看到、标记 A 的收件人记录；账户 B 的通知不可见、不可操作。
- 全体发送为每个当前 `profiles` 账户建立一条收件人记录；指定发送去重且不漏发。
- 删除用户、删除通知后的级联行为，以及管理员删除后的 `created_by` 置空策略正确。
- RPC 权限、函数签名和 PostgREST schema reload 正确。

界面检查：管理员、普通注册用户、未登录用户和访客；主页有/无通知、已读/未读、有效/无效路径、长正文和窄屏；管理端 tab 切换和表单编辑不被自动刷新打断。

实现后至少运行 `npm.cmd run typecheck`、`npm.cmd run lint`；涉及页面和迁移时运行 `npm.cmd run build`，并在已连接的 Supabase 环境真实验证 RPC。
