# 指定 Arena 房间实施计划

状态：规划，未实施。更新日期：2026-10-10。

本文整理已确认的需求、与普通房间的差异、建议方案和待确定事项。建议方案不等于已确认产品规则；现有实现依据本地代码和迁移核对，未在本次查询线上数据库。

## 1. 目标与适用范围

只给管理员指定的一个房间增加比赛机制，供六名 Agent 选手游玩。普通房间继续沿用现有行为。比赛无需直播级提交顺序公平性；极少数模型返回顺序影响胜负的情况可事后依据记录人工处理。

建议后台配置绑定稳定的 `rooms.id`，房间号只用于进入和展示。创建 Arena 或更换指定房间只能通过受保护的管理员服务端入口。配置方式、指定房间关闭后的处理方式尚待确定，不自动将其他房间升级为 Arena。

## 2. 哪些不一样

| 项目 | 普通房间 | 指定 Arena 房间 |
| --- | --- | --- |
| 房间号 | 随机生成 | 希望管理员可自定义，最低优先级 |
| 开题时间 | 保持现有手动开题 | 管理员可预选题目和指定时间，由服务端自动开题；到时前不能提前揭示或启动该题 |
| AI 请求并发 | 同房间最多 1 个，忙碌时拒绝 | `ask + hint + reason` 共用最多 8 个处理中名额 |
| 单个选手 ask | 沿用现有规则 | 上一条 ask 未回答前，不能提交新的 ask |
| 等待 ask 时的其他操作 | 沿用现有规则 | 允许 hint、reason，仍受房间总并发及其他既有校验限制 |
| ask 最终裁决 | 双模型一致采用，不一致仲裁；可命中已批准缓存 | 收到即启动双模型；人工逐题 5 秒裁决，连续三次超时转自动 AI |
| 管理员操作 | 现有后台 | 新增隐藏页面 `/admin/select`，只展示指定房间裁判任务 |
| 正确 reason | 沿用现有通关流程 | 第一个正确结果成功在数据库结束本轮并记录胜者，不等待更早提交的推理 |
| 比赛结束 | 沿用现有流程 | 取消尚未执行任务；拦截迟到结果，并按明确结算规则释放名额与退款 |
| 超出 8 个请求 | 不适用 | 原需求为有界等待队列；是否首版改为忙碌拒绝尚未确认 |

六名选手意味着最多六条 ask 同时等待回答，并不为 ask 固定预留六个并发名额。hint/reason 可以先占用名额；所有模式合计始终不超过八个。八是处理中上限，不是等待队列容量，也不是 DeepSeek API 调用数量上限。

## 3. 哪些保持一致

- 现有网页与 CLI 入口、请求校验、消息展示及玩家输出脱敏继续使用；不能只修改网页而遗漏 Agent 使用的 CLI/API 路径。
- 现有登录、游客 Cookie、房间成员校验、设备锁和接管机制不因 Arena 而放宽。
- 管理员继续使用现有管理员身份、邮箱验证码与可信设备机制；隐藏地址不是权限控制，页面及所有读写接口都要验证管理员权限。
- 房间名称、座位、加入密码、积分价格与支付来源、提示机会、字数限制和每座位现有频率限制，默认沿用现有规则。Arena 不自动免费或取消所有限流。
- 当前题目、汤面、汤底、key points、fact/inferential examples 与提示/推理 prompt 沿用现有体系。
- Strict 与 Inferential 仍是两个不同视角的判断；其调用目前已经并行。
- 玩家只看到最终回答和允许公开的事实；模型理由、内部裁决记录不返回玩家。
- 事务扣费、失败补偿、题目隔离、切题/关房后的迟到结果保护继续保留并扩展；不允许通过放宽表权限实现功能。
- 普通房间不启用人工裁判、八并发、Arena 胜者规则；保留普通房间现有缓存和裁判路径。

保持一致指业务规则不变，不代表公共代码完全无需调整；修改共享路径时必须验证普通房间行为未变化。

## 4. 人工裁判流程（已确认）

核心规则：模型判断提前并行进行，人工逐题处理。收到 ask 就调用 Strict 和 Inferential，不等待它排到人工队列第一位；只有成为人工队列第一位才开始五秒倒计时。

1. 玩家提交 ask，完成成员、题目、单人未回答 ask 与房间容量校验；接受后持久保存任务，优先以最低延迟通知管理员，同时启动 Strict、Inferential 两路调用。通知和模型调用不能互相等待；模型启动不受人工队列顺序限制。
2. 人工裁决开启时，将问题按服务器接受顺序加入人工队列。当前题目立刻展示，后续题目等待人工，但双模型已经运行，可以提前得到结果。
3. 题目成为人工队列第一位时，由服务器原子领取并保存人工开始时间、五秒截止时间。排队期间不消耗五秒；页面刷新或多个管理员标签页不能重复开始计时。
4. 当前题目尚未人工决定时，将已经返回的两路答案与理由显示出来，后续返回及时更新；可以先展示已完成的一路。模型提前完成不提前关闭人工窗口；管理员无需等模型即可回答。
5. 管理员在窗口内选择“是 / 否 / 与此无关 / 模糊问题”，立即锁定最终答案，连续未回答计数清零，并切到下一题。不等待模型、事实摘要或房间消息发布完成才切题。已经运行的模型即使返回也不能覆盖人工选择，不再启动仲裁。
6. 五秒未作人工决定，当前题目退出人工队列，交给自动 AI 并切到下一题，不等待当前题目的模型完成。自动路径等待两路判断，一致则采用，不一致再仲裁；未完成的模型不延长人工窗口。
7. 连续三条实际进入人工窗口的 ask 都超时未回答，自动关闭人工裁决。第三条及后续尚未进入窗口的任务走自动 AI；等待人工的队列不再逐题额外等待五秒，新 ask 也直接走自动 AI。
8. 最终回答向整个房间发布。人工选择是或否时复用 `requestFactSummary()` 自动生成事实摘要；摘要不得改变答案，失败不阻止回答发布。

例：A、B、C 接连到达，三条的双模型均立即开始。人工先看到 A 的五秒；A 决定后 B 才开始自己的五秒，B 可能此时已有模型结果。A 超时也立即让 B 进入窗口，A 在后台继续自动判断。连续 A、B、C 均未回答后，后续问题直接自动回答。

管理员可以在模型尚未返回时直接选择。若当前问题两路均耗时超过其人工窗口，可能没有可参考的模型结果。自动结果即使提前准备好，也不能在对应人工窗口结束前抢先锁定。

建议以数据库服务器时间判断裁决是否在窗口内，以服务器接受裁决为准；浏览器倒计时仅作展示。窗口到期与人工提交的竞争必须在数据库原子处理，不能依赖页面按钮是否禁用。最终裁决与人工队列推进分开记录，避免人工已决定但发布暂时失败时阻塞下一题。已被接受的人工决定不允许被后续点击覆盖。

### 连续未回答计数与恢复

连续三次的触发规则已确认，建议计数只增加于真实人工窗口超时，每次成功人工决定清零；模型失败、题目取消、切题和关房不能当作管理员未回答。超时推进、计数更新与第三次切换自动模式必须原子执行，重试不重复计数，多标签页也只能共同处理一个当前题目。

关闭人工裁决后怎样重新开启尚未确认。建议 `/admin/select` 提供“恢复人工裁决”按钮，显式恢复并清零计数，不因页面重开自动恢复。恢复仅适用于之后的新任务，已经进入自动处理的任务不重新获得人工窗口；是否新一轮默认恢复也待确定。

### 裁判页面

突出一个当前问题：提问玩家、问题、所属本轮、Strict/Inferential 答案及理由、各路等待/失败状态、五秒倒计时和四个快捷裁决按钮。另提供精简待裁决列表，问题收到就出现，不等模型返回；队列后面的模型结果可以提前保存，不同时开启多个倒计时。

显示当前人工/自动模式、连续未回答次数和已决定反馈。手动选择或超时后立即切到下一题，不能因列表移动将上一题的点击应用到下一题；所有裁决绑定明确任务 ID。自动模式下不再展示可提交的人工窗口。

优先复用现有受保护刷新机制，可用 Realtime 提醒刷新，但必须支持断线后的受保护补拉。尽快推送问题正文，模型理由后到后补，不先等待双模型、摘要或低频整页刷新。截止后禁止新裁决；页面重开不能重新获得五秒。管理员页面断开时，后台仍需推进超时并在连续三次后切换自动模式，不能依赖浏览器定时器。

## 5. 并发、任务与积分

### 两层限制（已确认）

- 房间级：ask、hint、reason 合计最多八个处理中请求，等待人工决定也占用名额。双模型提前完成但尚未最终回答的 ask 仍占名额。
- 选手级：每名选手最多一条未回答 ask。失败或取消也必须释放限制，不能永久阻止后续提问。
- 接受请求和检查限制必须由数据库原子完成；只禁用前端按钮无法防止双击、重试和多入口绕过。

### 超限与执行方式（待确定）

人工裁决队列已确认存在，它只决定谁获得当前五秒窗口，不限制已接受 ask 的模型提前执行。它与超出八个请求时的执行等待队列是两回事。

原始要求是超出八个时进入有界等待队列，队列容量尚未指定。后续讨论认为占满八个是极端情况，提出过首版直接忙碌拒绝的简化建议，但用户尚未确认取消队列。最新“收到就调用”确定不等待人工队首；如果连超出八个、尚未获得处理名额的 ask 也立即调用模型，将与房间八请求上限冲突，此容量边界实施前需明确，不能默默突破上限。

- 若保留队列：定义队列总容量、每人额度、各模式顺序、排队超时、扣费时机与退出/被踢后的处理；排队中的 ask 同样占用选手未回答 ask 限制。任务必须持久保存，领取执行和释放名额具有幂等性，并具备可靠唤醒与故障恢复机制。
- 若直接拒绝：占满八个时不接受、不扣费，沿用忙碌提示；无需建立排队调度器，但处理中任务仍需持久裁决状态和失败恢复。

不能使用单个 Node 进程的内存计数器控制房间并发或保存人工决定，多个服务实例必须看到同一状态。数据库短事务锁用于接收、领取、裁决和完成，不在模型调用期间持有数据库事务。

### 结算与恢复

现有请求接受时就扣费，并更新 ask 次数、hint tokens；现有过期租约补偿可以复用思路，但不能直接把排队时长算成处理超时。

需要明确 queued/running/completed/cancelled/failed 等状态、处理租约、人工截止时间与单次结算记录。退款、取消、超时回收和模型正常完成可能同时发生，实际回答和退款都只能结算一次。是否恢复取消请求产生的提示机会及 ask 次数，需要与积分一起定义，不能只退积分。

## 6. 正确推理与本轮结束（已确认方向）

采用“正确判定先完成并成功写入者获胜”，不等待更早提交的 reason，也不按客户端时间排序。

数据库在同一个原子操作中检查本轮仍进行中、记录胜者并结束本轮。其他正确结果随后到达时，不再产生第二个胜者、获胜公告或重复奖励。保留提交时间、判定结果及最终胜者，极少数争议可事后处理，本期不新增专用改判界面。

必须使用本轮标识隔离任务，不能只比较 puzzle_id：同一道题重新开局也不能接收上一轮的迟到结果。

结束时停止接收本轮请求、取消尚未执行任务、关闭未完成的人工窗口，并阻止运行中的旧结果发布或改变状态。外部模型调用可能已发出而无法可靠撤回，数据库仍要拒绝迟到写入。尚未执行任务若已扣费必须退款；已开始未完成、已判定但未发布等情况的收费/退款与玩家提示待确定。

### Arena 指定时间自动开题（新增已确认需求）

仅指定 Arena 房间支持：管理员预先设置题目与开题时间，到指定时间由服务端自动开始本轮，不依赖管理员保持页面打开。普通房间保持现有手动开题行为。这是产品内的开题机制，不是 Codex 聊天的定时任务。

建议首版采用“一次性预约一题”：管理员选择题目、日期与时间，保存后可查看、修改或取消预约；不默认扩展为多轮赛程或周期任务。具体配置放在 Arena 管理界面的独立面板，是否与 `/admin/select` 同页实施时确定。

- 时间明确展示时区，建议默认 `Asia/Singapore`；数据库保存绝对时间，避免部署服务器时区影响。具体管理员配置时区待确定。
- 到时前可以展示开题倒计时，但预约不等于当前题目已开启。服务端必须阻止网页、CLI 和手动开题入口提前启动预约题目；不能只禁用按钮。普通聊天是否继续沿用现有规则，不因此自动开放 ask/hint/reason。
- 未开题前不向选手暴露预约题目的内容或可获取该内容的标识；倒计时能否展示题目标题另行确定。上一轮若仍运行，不将预约题目混入上一轮上下文。
- 到点由可靠的服务端调度触发，数据库再次检查房间为指定 Arena、预约仍有效、题目存在和执行时间已到，然后原子创建本轮并更新预约状态；多个触发、重试、刷新或服务恢复最多开题一次。
- 复用现有开题业务规则，并增加 Arena 预约与本轮标识；不能直接设置 current_puzzle_id 跳过进度、上下文和状态初始化。
- 预约修改/取消与到时触发必须原子竞争，按数据库接受顺序决定结果。已经开题的预约不能再当作未执行预约修改。
- 房间关闭、指定 Arena 被更换、题目被删除或上一轮仍未结束时不能静默覆盖现有状态。建议取消或标记失败并在管理端显示原因；是否到点强制结束上一轮尚未授权，默认不强制切题。
- 调度延迟时不能早开；允许迟到多少、是否在恢复后补开或过期取消，实施前确定。调度方式与精度按实际部署能力核实，不能仅靠浏览器 setTimeout 或整分钟调度声称秒级准点。
- 新一轮是否重新开启人工裁决及清零连续未回答计数，沿用本计划的待确定项，不因自动开题自行决定。

验收需覆盖到时前拒绝提前开题、管理员离线仍自动开题、重复触发不重复开题、修改/取消竞争、关房/删除题目、上一轮未结束及调度中断恢复。网页和 CLI 都应在同一个本轮真正开始后才允许针对该题提交 AI 请求。

## 7. AI、事实与缓存边界

- Arena 按每题双视角判断的要求，建议绕过直接返回答案的问答缓存；缓存命中不能跳过人工窗口。普通房间缓存行为保持一致。
- 当前 `askWithCrossCheck()` 内部把两路结果、仲裁和摘要串成一次返回，需要拆出可逐路保存结果和独立提交最终答案的流程。
- 人工回答是或否可生成事实摘要，但不自动等同于“可进入全局问答缓存”。建议先独立审计，不自动将人工裁决写入共享缓存。
- 并发请求可能读取相同的旧事实快照，hint 也可能重复。建议每次开始处理读取本轮已发布上下文，仅已确认的最终回答可形成事实，禁止将未裁决结果当作其他请求的事实。
- 六名选手各一条 ask 可产生十二个判断调用，另有仲裁、摘要及 hint/reason；需统一管理实际 API 并发、超时和失败，避免无限重试。API 具体额度实施时核实。
- 单路失败、双路失败、仲裁失败的自动降级规则待确定；失败状态必须如实显示，不能把另一路结果复制成两个模型都返回成功。人工已接受的答案不应因模型失败而被撤销。
- 摘要应独立容错，建议先发布答案再补摘要；补写必须检查本轮和最终答案状态，且不能产生第二条回答或重新扣费。

## 8. 实施顺序

1. 确定下节边界规则，完善任务状态转换、数据库权限、取消和补偿合同。
2. 增加指定房间配置、本轮标识、任务状态与原子并发/单人 ask 限制，保留普通房间路径。
3. 拆分双路判断和最终裁决，接入模型提前执行、单题五秒窗口、连续三次超时切自动模式、管理员受保护接口及 `/admin/select`。
4. 完成八并发执行、超限策略、唯一胜者、本轮结束清理和网页/CLI 结果恢复。
5. 接入事实摘要、审计及缓存隔离，完成故障与普通房间回归验证。
6. 加入 Arena 一次性预约开题、服务端到时触发与幂等开题；验证提前访问限制、取消竞争和调度恢复。
7. 最后添加可选自定义房间号。优先保持六位大写字母/数字格式，避免修改所有房间路由与客户端协议。

所有数据库变化通过新迁移交付；上线前预览，部署后核对实际函数、授权和预期角色调用。本文不授权实施、迁移或部署。

| 超限 ask 是否立即调用模型 | 在八名额内收到即调用、不等人工队首已确认；超过八名额时的接收与启动规则需与超限策略一起确定 |
| 人工模式重新开启与跨轮行为 | 建议显式按钮恢复并清零计数，自动处理中的任务不倒退；新一轮是否恢复待确定 |
| 指定房间怎样创建、关闭后是否更换 | 建议管理员配置绑定 rooms.id，变更仅在无活动本轮时进行 |
| 选手身份及每人额度 | 预期六名选手；建议按稳定成员身份限制，避免换座重置，账号/游客与重入规则需明确 |
| 排队扣费与取消补偿 | 需定义积分、提示机会与 ask 次数的一致结算 |
| 已执行请求在比赛结束时如何计费 | 未执行且已扣费任务退款；其余分支待确定 |
| 模型及仲裁失败策略 | 需定义降级或退款；不影响已经接受的人工决定 |
| 结果与事实摘要的发布时间 | 建议答案先发，摘要独立补写且失败不阻塞 |
| 自动开题配置与精度 | 指定时间自动开题已确认；建议一次性预约，时区、容许延迟、过期补开及上一轮未结束时的处理待确定 |
| 当前每座位三秒频率限制 | 默认保留；仅在有明确需求时单独修改 |

## 10. 验收清单

- 普通房间仍为单请求处理，不出现 Arena 人工窗口，缓存与积分规则正常。
- 六名选手各一条 ask 可同时处理；同一选手重复 ask 被原子拒绝且不重复扣费；等待 ask 时仍可 hint/reason。
- 多模式合计最多八个；第九条按最终确定的策略处理；多服务实例和客户端重试不突破限制。
- 收到 ask 即通知管理员并启动双模型，不等待人工队首；成为人工队首才开始五秒，刷新和重连不重置窗口。
- 同时到达多条 ask 时只有当前一条人工倒计时，其他模型照常运行；人工决定或超时立即推进下一题，不被模型或摘要拖住。
- 连续三次人工窗口超时只切换一次自动模式；一次人工成功打断连续计数；取消不误计，管理员离线也能自动推进。
- 切换自动模式后积压及新问题不再等人工五秒；恢复方式按最终合同验证，多标签页不重复裁决或推进。
- 人工早于模型、模型早于人工、临近截止同时提交均符合优先级；人工成功后不仲裁、不被覆盖。
- 单路先返回可立即显示；超时后才齐结果可自动判定；单/双路失败与仲裁失败按合同结算。
- 人工是/否的摘要失败仍发布正确答案；摘要不改变答案或污染其他本轮。
- 两个正确 reason 同时完成只有一个胜者；重复完成请求不重复公告和奖励。
- 比赛结束、切题、同题重开、关房、成员退出/被踢、运行进程中断均不产生旧答案、重复退款或永久占用。
- Arena 到时前不提前开预约题目；管理员离线可自动开题，重复触发只产生一轮，取消/修改与调度失败按合同处理，普通房间无此行为变化。
- 未验证管理员不能读取模型理由或裁决；玩家消息接口不暴露内部审计。
- 网页和实际 CLI/Agent 都完成对应流程；分别报告本地检查、远端迁移、部署与真实付费 E2E 结果。
