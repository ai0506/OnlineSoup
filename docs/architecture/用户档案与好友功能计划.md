# 用户档案与好友功能计划

> 状态：规划中，尚未创建数据表、迁移或页面。本计划以当前已实现的账户、房间、通知规划为边界。

## 1. 当前基础与限制

当前注册用户在 `profiles` 中已有全局唯一用户名、显示名、积分、注册时间、最近登录信息和单会话标识。站点头部已链接到只属于当前登录用户的 `/profile`；该页已有个人操作统计、通关记录和积分流水。

房间座位 `room_seats.user_id` 已能标识注册成员，且房间界面已经区分“已注册”和“访客”。这可作为好友申请的可靠来源。相反，系统目前没有公开用户页、用户目录、好友关系、私信或头像存储。

以下资料只能由本人或管理员看到，不能因为增加公开档案或好友功能而泄露：积分和积分流水、最近登录地点/设备/IP、活跃会话、反馈内容、后台邮件地址、房间私密信息，以及游客 Cookie/会话信息。

聊天记录只存了发送时的昵称、座位和注册/访客类型，不含稳定的发送者用户 ID；而座位会随离开而释放。因此第一阶段不能承诺为历史聊天准确补显示头像，也不应以昵称反查用户。

## 2. 产品范围

### 第一阶段：个人资料增强（建议优先实现）

仅对已登录注册用户开放：

- 在 `/profile` 展示一个稳定、可识别的预设头像，及用户名、加入日期和已有统计。
- 提供“编辑资料”小面板，允许选择预设头像和填写简短个人简介（例如 0–80 字）。
- 资料保存后，站点头部及本人档案即时使用头像；房间座位可在不改变昵称和身份逻辑的前提下显示小头像。
- 预设头像采用服务端限定的 `avatar_key`（图形/颜色组合），不接受任意图片 URL、SVG 或 HTML。

第一阶段不做真实图片上传。这样无需新增公开 Storage bucket、图像审核、文件清理、尺寸处理、CDN 缓存失效或恶意内容处置；日后确有需求时可独立增加上传方案。

### 第二阶段：公开的最小档案

为已注册成员提供只读路由，例如 `/users/[username]`。仅返回：用户名、预设头像、公开简介、加入月份和已同意公开的汇总统计。默认不展示积分、登录信息、精确通关时间、所在/历史房间、邮箱或内部 ID。

入口只放在“当前房间中的已注册成员”处和好友列表中；不做全站用户目录或模糊搜索。若以后需要检索，仅支持精确用户名匹配，且不返回邮箱和不存在用户名的可枚举细节。

### 第三阶段：好友（先服务于一起玩）

好友不是即时通讯系统。初始能力仅包括：

- 在同一房间的已注册成员资料卡中发起好友申请；访客不能被添加，也不能发起申请。
- 申请方可取消；接收方可接受或拒绝；双方可解除好友。
- 通过全局顶部的“好友”图标打开独立的好友中心抽屉；抽屉覆盖在当前页面之上，不跳转到 `/friends`，不刷新房间或大厅。
- 已接受好友资料卡可提供“复制房间链接”或在未来房间创建流程中作为邀请对象；本期不自动拉人进房，也不绕过密码、座位、单会话、房间人数或积分规则。
- 好友申请/接受结果复用规划中的站内通知，在主页可见；通知只是提醒，关系表才是唯一事实来源。

首期不做私信、动态、关注者、点赞、排行榜、陌生人推荐、在线状态或“最近一起玩过”。这些功能会扩大隐私、骚扰治理和 Realtime 成本，应在好友核心链路稳定后单独评估。

### 顶部图标与好友中心交互方向

全局顶部只保留“汤局”作为文字品牌和返回大厅入口；其余可操作项目收敛为图标按钮，不能只用无含义的 emoji 或文字首字母。建议的第一版层级：

| 位置 | 图标含义 | 行为 |
| --- | --- | --- |
| 品牌 | 汤局 | 返回大厅，替代重复的“大厅”文字链接。 |
| 导航 | 教程（书本） | 仍打开教程页面。 |
| 主操作 | 创建房间（加号/门） | 仍进入现有创建房间页。 |
| 社区 | 通知（铃铛） | 打开规划中的站内通知二级抽屉，并显示未读点。 |
| 社区 | 好友（双人） | 打开好友中心二级抽屉；待处理申请显示数量徽标。 |
| 账户 | 头像 | 打开账户小菜单：个人档案、积分、反馈、退出；积分不再占用顶部文字。 |

“全部图标化”仅适用于顶部的高频操作。图标必须同时具有可见悬停提示、`aria-label`、键盘焦点态和至少 44×44px 点击区域；抽屉内部仍应使用清楚的文字标题、申请人用户名和操作按钮，不能让用户猜图标含义。

好友中心是新的独立界面组件，而不是路由页面：桌面端从右侧滑入，宽度约 360–420px；手机竖屏占满或接近占满宽度。关闭按钮、遮罩点击和 Escape 均可关闭；打开后将焦点移入抽屉、关闭后回到触发图标，并避免在房间聊天输入时因刷新或重渲染中断输入。

抽屉首次打开才通过受保护的服务端 Route Handler 或 Server Action 读取 `get_my_friend_overview()`；关闭时保留当前页面，后续成功操作局部更新抽屉数据。`SiteHeader` 当前是服务端组件，实施时应保持它只读取当前用户的最少资料，再把图标栏和抽屉状态交给新的客户端组件管理，而不是把好友表开放给浏览器直接读取。

## 3. 建议的数据模型

### 3.1 资料字段

在 `profiles` 追加低风险、默认值明确的字段：

```text
avatar_key       text not null default 'default-01'  -- 受限枚举
bio              text not null default ''            -- 0–80 字，纯文本
profile_visible  boolean not null default true        -- 为后续公开档案预留
```

也可将公开字段放入独立的 `profile_public` 表；但现有 `profiles` 已是账户主记录，且其 RLS 已限定“只可读自己”。为避免读取规则复杂化，建议继续将敏感字段留在 `profiles`，通过专用 `get_public_profile(username)` RPC 仅投影允许公开的字段，而不是放宽 `profiles` 的 select 策略。

### 3.2 好友关系

建议使用一张定向申请表，而非两个“好友列表”副本：

```text
friend_requests
  requester_id uuid references profiles(id) on delete cascade
  recipient_id uuid references profiles(id) on delete cascade
  status       text check (status in ('pending', 'accepted', 'rejected'))
  created_at   timestamptz
  responded_at timestamptz null
  primary key (requester_id, recipient_id)
```

关系的增删改全部经过原子 RPC。创建请求时，对按 UUID 排序后的双方取得 advisory lock，并检查任意方向已有记录；这样能阻止两人并发互相申请而留下两条 pending 记录。已接受关系在查询时按双方任一方向合并为一个好友。

如果后续发现拒绝后反复骚扰的实际问题，再增加独立 `user_blocks` 表；不要把“拒绝”误作永久拉黑，也不要在第一版仓促引入复杂的双向状态机。

## 4. 权限与接口边界

新表均启用 RLS，浏览器不直接写关系表或档案敏感字段。建议的接口：

- `update_my_profile(avatar_key, bio, profile_visible)`：仅修改 `auth.uid()` 对应资料，校验 avatar 枚举与纯文本长度。
- `get_public_profile(username)`：仅返回白名单字段；不可返回内部 UUID、积分或登录元数据。
- `send_friend_request(target_user_id)`：要求双方为不同的注册用户，并在单一事务内处理重复/交叉申请和通知创建。
- `respond_to_friend_request(requester_id, accept)`：只能由接收者处理自己的 pending 请求。
- `cancel_friend_request(recipient_id)`、`remove_friend(friend_id)`：只能影响调用者所属关系。
- `get_my_friend_overview()`：仅返回调用者的好友、收件箱和必要的公开资料投影。

若必须使用 `SECURITY DEFINER`，函数须设置空 `search_path`、先撤销 `PUBLIC` 执行权限、再只授予 `authenticated`；所有用户 ID 从 `auth.uid()` 推导，不接受客户端提交的“当前用户 ID”。所有函数签名变动后通知 PostgREST 刷新 schema。

## 5. 与已有功能的衔接和冲突处理

| 既有部分 | 可复用点 | 不可突破的边界 |
| --- | --- | --- |
| `/profile` 与 `get_my_profile_page` | 可先扩展本人资料页和统计卡片 | 仍只读取本人私密资料；公开资料要走单独、字段白名单的接口。 |
| `profiles` 与全局用户名 | 用户名可作公开路由和显示标识 | 用户名只能 3–8 位，修改时受活跃房间限制；好友关系必须用 UUID，不能用可修改的用户名。 |
| `room_seats.user_id` | 同房间已注册成员可安全成为申请入口 | 不将访客昵称、Cookie 或座位 ID 发展成站内社交身份。 |
| `room_messages` | 当前聊天可保留注册/访客标签 | 不以历史昵称绑定档案，也不在本期改造所有 AI/系统消息写入路径以追加头像。 |
| `SiteHeader` 与现有图标组件 | 已有站点头、悬停提示、内联 SVG 和对话框样式可沿用 | 当前头部是服务端组件且文字链接较多；不得把好友数据预加载到所有页面，也不能用无标签图标降低可访问性。 |
| 站内通知计划 | 好友请求与处理结果可投递到主页 | 不把通知表当好友状态；没有通知也不得影响请求/接受的真实结果。 |
| 管理后台账户功能 | 管理员可在必要时查看关系审计和处理举报 | 不把普通用户的好友列表或私密资料开放给后台默认列表，更不能复用管理员邮件发送能力。 |
| 账户删除清理 RPC | 现有删除流程已有前置清理入口 | 新关系外键必须 `on delete cascade`，并将相关通知/审计清理加入同一删除验证。 |

## 6. 分步实施与验收

1. **资料预设头像**：迁移、RPC、`/profile` 编辑面板、头部和当前座位的小头像；验证游客、未设用户名用户、刷新和头像参数篡改。
2. **公开最小档案**：增加资料卡/路由和白名单 RPC；验证他人永远无法取得积分、登录信息、UUID 和积分流水。
3. **图标栏与好友中心外壳**：在不改变现有页面 URL 的前提下，替换顶部文字操作为带标签的 SVG 图标，建立可访问的二级抽屉；验证键盘操作、手机尺寸、房间页聊天输入和未登录态。
4. **好友核心流程**：关系表和 RPC、房间成员资料卡入口、好友中心的待处理/好友列表、与站内通知的事务内写入；验证双向并发申请、自我申请、重复申请、拒绝/取消/解除、被删号清理。
5. **邀请体验**：仅在好友已接受后给出房间链接或创建房间后的选择器；端到端验证仍会执行原有密码、满员、同账号房间接管和积分检查。

每一步都单独上线、单独回归房间加入/退出/踢人/换座、聊天、个人积分和管理员删除用户流程。不要把好友功能与自定义汤、BYOK 或真实邮件推送绑定为同一批改动。
